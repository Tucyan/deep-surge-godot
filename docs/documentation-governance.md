## 文档职责与读取顺序

| 层级 | 内容 | 维护方式 |
|---|---|---|
| 根 AGENTS | 长期协作约束、执行/仓库边界、关键禁区 | 保持精简，链接详细契约，不追加工作流水 |
| 根 README | 当前工程和独立历史仓库导航 | 工程入口改变时更新 |
| 工程 README | 启动、模式、保存范围、常用验证 | 始终描述当前行为，历史变化移入归档 |
| 当前主文档 | 机制、架构、Agent、剧情/保存、回廊 | 每个主题一份主文档；其他位置摘要并链接 |
| 专题参考 | 某功能的规则与表现细节 | 标明适用范围，旧验证不冒充当前验收 |
| design / plans | 提案、实施过程和待验证目标 | 明确提出/已实施/部分验收，不能仅因写进计划就声称完成 |
| evidence | 当次版本、命令、结果和限制 | 历史证据保留，不随新版本自动改成通过 |
| archive | 被取代的上下文和增量说明 | 保留原文，不作为当前实现入口 |

默认先读索引和相关主文档，再按任务查专题、代码及测试；不必加载全部计划、历史日志、证据和机器环境。根仓库、Godot 和历史工程继续各自保留 Git 边界。

## 当前契约登记

[documentation-map.json](documentation-map.json) 列出当前主文档和核对来源。登记文档在标题后保留一行 HTML 元数据：

```html
<!-- doc-status: current; doc-role: contract; content-version: godot-flow-v02-26; reviewed: 2026-10-19 -->
```

`doc-role` 为 entry、contract 或 governance；内容版本必须与 GameSession 一致，reviewed 使用实际核对日期。版本变化后检查失败是提醒重新核对，不应只批量更新版本号/日期而不检查内容。

未登记的专题先检查链接，其标题里的功能引入版本和旧验收结论不会自动升级为当前全局契约。只有完成相应范围核对后才登记为当前主文档。当前文档描述已实施行为；发现代码、测试与文档冲突时说明差异，确认预期后同步修正，不机械地把任一方当作无条件正确。

## 更新与归档规则

1. 修改规则/接口时先确定负责该主题的主文档，更新正文和关联测试入口；入口摘要链接主文档，避免复制数值表和多份流程。
2. 当前正文保留最终行为；旧的“vX新增/后段覆盖前段”移入 archive 或历史记录，保留来源和日期。
3. 实施计划记录实际状态；验证记录写清执行版本、命令、失败/跳过及未覆盖范围，索引只导航到记录。
4. 重组前保留原文快照；历史原文缺少的设计源不得伪造。当前文档改为链接实际代码或可用资料，并说明原来源未随仓库提供。
5. 文档修改运行以下检查；涉及规则或表现变更时另外运行对应 Godot/内容/GPU 验收。

```powershell
python tools/check_docs.py
python -m unittest discover -s tests -p test_check_docs.py -v
```

检查器只使用 Python 标准库，不启动游戏、不访问网络或玩家存档。默认检查工程 README、docs 顶层专题，以及嵌套工作区存在时的根 README/AGENTS 的本地 Markdown 目标；登记的主文档额外验证角色、日期、内容版本和来源路径。示例代码块不当作真实链接。

它不检查外部网站可用性、全部 Markdown 锚点、自然语言规则是否与执行语义完全一致，也不证明运行测试通过。plans、evidence 和 archive 不做当前版本一致性检查；历史文件作为链接目标仍需存在。
