# 0.3 分层与配置解耦审查提案

日期：2026-10-20。状态：**静态审查与设计提案，未实施玩法，未进行0.3平衡试玩**。

后续正式更新范围见[0.3更新范围定稿](v03-release-scope.md)。本页保留审查来源与架构分析，不替代定稿，也不代表已实施。

核对工程：Godot `codex/origins-v1`，内容版本 `godot-flow-v02-26`。当前行为以[当前机制](../current-game-mechanics.md)为准。本页提出未来边界，不将讨论当成运行契约。

## 1. 已确定方向与待定参数

用户提出三层航程：Ⅰ偏低难度、5次航行与弱Boss；Ⅱ中等难度、10次航行与困难Boss；Ⅲ暂为最终层、10次航行与困难Boss。层级在游戏中仅显示罗马数字。更高基准航耗、恶劣环境、更多普通战斗和全战斗候选航次提供持续压力。战斗遭遇撤离计划扣4生命；宝箱打开后70%困难战斗、暴雨每航次损坏2～3格并增加饱食消耗为用户提出的内容方向。用户补充明确：宝箱作为普通节点出现，不单独设计宝箱系统；需要通用的节点触发战斗接口。

饥饿、缺水分别累计归零结算次数；恢复期间不增长、不清零，再次归零继续递增。每项伤害上限为平衡配置，默认5，整数值<=0表示无上限；上限约束实际伤害，不截断累计次数。两项同时归零时，默认单航次合计最多10生命。旧实现的合计2点伤害上限不能继续截断新规则。

本提案建议累计次数跨层保留、新局清零；不因读档、查看、取消或转层再次结算。层航次数包含末站Boss、转层无额外免费生产/恢复等仍属建议边界。前文讨论的各层食水20/30/40、暴雨持续2次航行/额外饱食15、先奖励后埋伏均为助手试测建议，尚非用户确认数值。上限设置指内容平衡参数，不自动增加玩家设置页选项。

## 2. 节点池必须与节点内容、抽样策略分离

当前[候选规则](../../core/encounter_rules.gd)遍历全局nodes表；节点类别权重、候选数3、前两航次免费食水优先、同族去重、重复衰减等在同一模块中。节点表虽有`pool`历史字段，当前抽样不按它选池。

建议采用以下所有权：

| 对象 | 拥有的数据 | 不承担的职责 |
|---|---|---|
| 节点定义 | 稳定ID、文字、选项、条件、效果、随机分支、战斗引用 | 不判断自己属于第几层 |
| 节点池/投放档 | 可投放的节点或变体引用、类别/条目权重、开放窗口、投放配额 | 不复制整份节点正文 |
| 候选策略 | 候选数、普通/全战斗组合、保底、同族限制、回退 | 不修改节点效果 |
| 层定义 | 引用节点池、候选策略、Boss遭遇、环境档及数值修正 | 不直接实现开箱/伤格/战斗逻辑 |
| 访问实例 | 唯一visit_id、已选分支、阶段、实际生成奖励/战斗、已解决状态 | 不写回共享定义 |

同一营地可在Ⅰ和Ⅱ复用，投放频率不同；有不同奖励或敌人的实质内容变体需显式变体ID或奖励/遭遇档，不允许临时改写全局节点。投放配置只覆盖白名单字段；内容定义的硬限制不能被任意覆盖。

尤其需要独立配置三类规则：

1. **次数范围**：每局最多、每层最多、冷却分别声明。当前营地最多1次、商店最多2次均按整局计数，直接延长到25站可能让后两层无此类补给。可以同时设置整局硬上限与层内配额；计数按稳定ID及明确family/variant作用域保存。
2. **时间范围**：开放门槛明确使用全局航次或层内航次。当前节点和选项`min_voyage`均读全局voyage；不能在转层时偷偷改语义。全局冷却跨层连续，层内窗口用独立layer_voyage。
3. **候选组合**：提高battle权重不等于本次全是战斗；全战斗航次是独立抽样策略，可有频率、连续次数限制与合法池。只含可免费离开的战斗入口也不等于强制承压。

抽样建议顺序：模式/固定站覆盖 → 当前层允许池与内容合法性 → 全局/层内次数及窗口 → 候选组合和保底 → 权重与出身修正 → 去重/填槽 → 生成实例并固定可见性。保底从该层合法池中选，战斗狂不能将Ⅰ禁止的强敌补回来。固定Boss优先于普通组合；早期补给保护与全战斗冲突时，保护优先或禁止两者在同一窗口同时启用。空池使用显式回退，不为补满三个候选跨层抽取。配置加载时发现保底不可能满足，应明确报配置错误；运行中池耗尽使用约定回退。

当前`OriginRules.battle_weight`对战斗狂直接返回30（现行基准20时等效+50%），并非实际乘1.5。节点池支持不同权重后需改为明确的出身相对修正，避免层战斗权重提高后反被固定30覆盖。

### 天气覆盖候选与临时战斗补位

用户提出的扩展示例：某天气将战斗节点出现概率提升至100%，当前池战斗节点不足时，额外生成临时战斗节点。本节按“每个候选槽均为战斗”理解；与“至少提供一个战斗候选”使用不同策略字段，不共用含混的概率。

**当前运行代码不能仅靠配置完成该行为。** EnvironmentRules尚无候选类别强制接口；EncounterRules仅按全局权重抽样，没有临时补位；RunRules.valid_node要求实例对应目录nodes定义且正文一致，未知ID或任意拼装的临时节点不能恢复。现有环境先于候选生成、候选唯一visit_id、统一dispatch/战斗执行与随机快照可复用，无需增加平行玩法内核。

建议让天气效果提供候选约束请求，由同一个候选生成器集中解析：

```text
天气效果：本次所有普通候选必须为battle
缺额策略：从指定临时战斗模板档补足

当前层合法普通战斗 → 按正常配额/冷却/去重选择
不足目标候选数量 → 由临时战斗模板生成缺额实例
最终候选 → 固定visit_id/敌人/奖励/来源 → 统一迷雾投影与保存
```

新增设置的所有权：天气定义引用候选覆盖/补位策略；层决定可出现哪些天气及允许的临时战斗档；模板档定义合法敌人、奖励、退出策略与可重复规则；候选生成器只负责解析约束与补位。普通池外的模板必须通过显式引用授权，不能为保证100%而随意放入更高层敌人。临时节点不回写共享池，也不需要为每种天气写一套节点生成逻辑。

具体规则建议：

- 补足目标候选数，例如3槽缺2则生成2个，而非在3槽外额外追加。模板数不足时是否可复用模板/敌人需显式允许；来源去重与普通节点同族去重分别处理。合法模板为零且要求100%时应视为不可满足配置，不悄悄补非战斗。
- 临时实例带稳定template_id、来源天气/策略ID、唯一visit_id与已解析参数。保存校验按受控模板和参数白名单重建比对，不接受任意敌人/奖励字段。模板与策略参与内容指纹；不放松现有所有节点的完整性校验。
- 未选实例随本次候选释放；选中的实例保留至其战斗、节点结果与收尾所需流程完成，避免因导航候选清空或天气到期而丢失当前战斗。临时是本次投放生命周期，不表示战斗奖励自动变成临时卡。
- 生成、展示候选不算访问、不发奖励。实际进入后按临时来源的配额策略计数，不能借用普通节点ID绕过其整局硬上限；胜利奖励走正常战斗结算。
- 使用已有nodes随机流生成一次并保存，查看/加载不重抽；环境刷新不能重新生成已经展示的当前候选。节点获得的待生效天气按既有规则从下一航次影响生成。
- 教程与层末固定Boss优先；天气100%约束对适用普通航次是硬约束，出身权重不能插入非战斗。若仍保留早期安全保护，应禁止此天气在保护窗口生效，或在配置中明确其覆盖关系，不能同时承诺全战斗与非战斗保底。

该接口也可表达某天气只提高战斗权重、保底至少一个战斗，或将商店类别暂时排除；软权重、硬类别限制与缺额补位分别声明，不用极大权重模拟100%。

## 4. 建议的配置引用结构

以下为结构示意，文件名/字段名尚未实施：

```text
航程 challenge_v03
  layers → [opening_sea, pressure_sea, final_sea]

层 opening_sea
  voyages → 5
  node_pool → opening_nodes
  navigation_profile → development_routes
  environment_profile → mild_weather
  boss_encounter → opening_boss
  survival_modifiers → 明确的逐项数值修正
  transition_profile → continuous_voyage

共享生存规则
  base_cost → {hunger, hydration, sanity}
  deprivation → {start_damage:1, step:1, max_damage:5}
  deprivation_state → 饥饿/缺水各自累计次数，属于存档

共享档
  战利品 / 成长 / 商店 / 补给 / 维修扩建
  默认档可被所有层共同引用
```

环境档允许的池只控制新增抽取，不自动清除上层带来的环境；若希望清除或转层休整，必须由转层策略显式声明。出身每局限制、扩建优惠次数、设备与燃料、生产进度、经验、遗物实例、伤格年龄、饥渴累计和随机游标默认连续。不要借转层重新运行new_game或initialization。

SAN出发支付与食水轮末结算保持不同时间点。基础费用/层修正/难度修正在出发时锁定；环境收费时点明确选定；遗物持有效果是否在轮末重算沿用当前契约或另作明确变更。预览和实际结算共用同一费用函数，并显示来源分项；禁止UI单独重算或新层覆盖已锁定的上层末站费用。食水最终各自下限0；比例修正若以后引入，必须声明乘加顺序和取整。

## 5. 需要特别补全的机制边界

- **Boss身份**：新Boss ID需显式标识Boss，避免只有名为boss才获得相应强化；进度门槛属于遭遇/层结束条件，不由敌人名字决定。Ⅰ弱Boss奖励与等级曲线需配套，防止首个Boss就跳多个等级。
- **节点触发战斗接口**：宝箱为普通节点定义，沿用选项、奖励与随机结果，不增加宝箱专属模块、命令、状态或判定。补全通用内部战斗请求，所有节点复用，见下节。现有随机next_stage可以转到另一个事件段落，但不自动等于强制开战。公开文字、可见奖励与隐藏后续分开；UI与Agent不通过raw outcome/battle字段泄露埋伏，公开的迎战选项仍正常展示。
- **暴雨**：需要明确每航次触发的唯一阶段，不能因进入战斗/重开页面再损伤。目标去重、完好格不足、是否可命中破损格、立即脱落或只破损、额外饱食费用及与其他环境叠加均在效果中声明。本次不擅自决定这些设计参数。
- **转层流程**：完成末站结果 → 老化/到期 → 容量整理 → 本航次生存结算 → 存活且满足层结束条件才切层 → 新航次AP/环境/生产/补给/候选各一次。Boss撤离后的终局或停留策略单列，不允许仅完成站点就自动跨过Boss。
- **模式边界**：本提案默认先供挑战0.3使用；剧情当前11站、教程3站不自动替换为25站。复用同一推进内核，引用独立配置。是否让剧情接入分层及如何映射节拍需要单独内容方案；旧剧情回廊契约继续保留。
- **保存**：保存当前层的稳定ID和位置、层内/全局航次一致性、Boss完成记录、节点配额、已生成候选/商店/分支及饥渴计数。新配置全部进入内容指纹；旧版本明确拒绝并保留原文件，不做迁移。
- **随机**：保留已有节点/奖励/战斗/环境/移动等独立可恢复流；层间不重置。配置解耦不自动保证“修改前层后，后层仍抽到同一结果”；0.3暂不新增按层播种体系，若需要此能力另设需求。
