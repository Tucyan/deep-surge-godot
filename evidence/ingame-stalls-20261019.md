# 局内交互卡顿检查（2026-10-19）

本轮仅诊断，没有修改游戏行为、提交、推送或导出。Godot 4.7.2、Compatibility、RTX 4060 Laptop GPU、窗口 1280×720；内容版本 `godot-flow-v02-26`，分支 `codex/origins-v1`、基准 HEAD `f5b513b925a7d5a353ac5aa4bdb82574fd18e377` 加现有未提交改动。结果属于当前工作区运行态，不代表干净提交或 Android 包。

## 方法与有效性

- [探针](../tests/probe_ingame_stalls.gd) 使用 seed22、standard/strong，隔离 APPDATA/LOCALAPPDATA，`persistence=false`。资源、容量、AP、商店和战斗采用受控夹具；夹具准备、恢复和等待不计入操作耗时。战斗为 60 HP biter，避免一次攻击终战混入结算。
- 最终扩展运行覆盖31类操作，每类进程内首样本1次及重复5次，共186个有效样本；失败数0，日志无 `SCRIPT ERROR` / `ERROR:` / `FAIL:`。规则不变的操作对比完整 state/profile（包括随机流），规则操作确认状态确实变化；检查按钮存在且启用、app无错误、收牌结束。
- 通过真实按钮信号/页面回调或 app 命令入口调用。材料选择走材料控件 `gui_input`，安装走木筏操作按钮，其命令延迟执行；不包含物理输入设备及系统输入队列延迟。商店预览调用页面同一处理函数，交易确认发出确认框信号。未做实际手指、鼠标拖拽体验验收。
- `draw_ms` 是调用前至下一次 `frame_post_draw`，包含主线程、调度和渲染；不等于纯 GPU 时间或端到端输入延迟。随后另测8帧最大间隔。首样本有启动资源预热，不是冷安装。
- 先前窄范围有效运行有120样本/失败0，见[初轮 JSON](ingame-stalls-20261019.json)。扩展运行的分层计时见[最终 JSON](ingame-stalls-detailed-20261019.json)，以最终运行作为下表来源。首次试跑因探针自身快照比较、入口和夹具错误中止，修正后才收集有效结果；没有把错误响应算作成功操作。

## 耗时来源

1. `flow_app.handle_ui` 中 `craft_tab`、`transmute_uids`、`transmute_target` 最终调用 `render()`；`PageHost._refresh_modal_only` 会移除原模态层，再通过 `_build_modal` 新建整页。底层HUD保留，但工作台的输入、图标、预览、目标列表和样式全部重建。可先改为更新投入计数、槽位、目标选中状态、预览和确认按钮；原有规则/随机不必变化。
2. `handle_command` 除普通出发局部路径外，状态改变通常走 `render()`；签名改变后 `PageHost.render` 移除原 layout、创建 game 页及仍开启的模态页。建议随后针对战斗动作、弃牌和经营操作分别定义需要刷新的区域，保留已存在控件和交互对象。不能绕过真实状态/报价更新。
3. 最终运行第4次投入木头：同步31.5 ms，render31.2 ms，其中 craft 页25.7 ms，hud_view0.88 ms，texture调用合计0.09 ms。确认攻击：同步82.5 ms，render80.4 ms，其中game页76.8 ms，hud_view0.93 ms，texture0.13 ms。确认购买：同步98.7 ms，render96.6 ms，其中game70.5 ms、shop20.4 ms，texture0.14 ms。页面构建是已测到的主要成本，不能据此归因图片磁盘读取、海面Shader或某一种控件内部实现。
4. 安装按钮 `_execute` 通过延迟调用提交命令，同步按钮调用仅约0.1 ms，但随后实际 render 中位66.7 ms，至绘制89.5 ms。只测按钮回调返回会漏掉这类卡顿。

分层数据相互包含：page构建与texture计时位于render内部，不能相加。`save_ms` 计的是 `_persist_profile` 包装层；本轮关闭持久化，**不测磁盘写入成本，不能据此断言真实自动保存不卡顿**。
